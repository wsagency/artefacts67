# Effect 4.0.1 on Cloudflare Workers

**Question.** Which Effect v4 APIs and runtime, error, cancellation, and resource constraints matter when migrating the existing Worker's Web Request/Response, D1, R2, WebCrypto, and Durable Object paths?

**Scope and version.** The npm registry record identifies `effect@4.0.1` as version `4.0.1`, an ES-module package whose root export is `./dist/index.js`; its package metadata has no runtime `dependencies`. Pin exactly `4.0.1`; this note does not treat prereleases as stable. ([npm registry: `effect@4.0.1`](https://registry.npmjs.org/effect/4.0.1), [package metadata](https://unpkg.com/effect@4.0.1/package.json))

## Effect v4 API facts that affect this migration

- `Effect<A, E, R>` is lazy: constructing an Effect does not execute I/O. It describes a workflow that can succeed with `A`, fail with typed `E`, and require services `R`. `Effect.gen` sequences yielded Effects with `yield*`, preserving those error, service, and interruption types. ([Effect 4.0.1 declarations](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [`gen` API](https://effect.website/docs/v4/getting-started/using-generators/))
- `Effect.fn` is the v4 function boundary for generator-based effect functions. The named form adds an operation name/tracing span; transforms after the generator receive the prior Effect and original arguments. It is an optional boundary/diagnostic tool, not a replacement for ordinary Worker functions. ([Effect 4.0.1 `fn` declaration](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [official `fn` API reference](https://effect.website/docs/v4/api/effect/Effect#fn))
- Wrap every genuinely fallible Promise binding with `Effect.tryPromise`. Its thunk is lazy, receives an `AbortSignal`, and maps thrown/rejected values to `Cause.UnknownError` when passed directly, or to the declared `E` when using `{ try, catch }`. A throwing `catch` mapper is a defect, so mappers must return an error value. `Effect.promise` is only for a Promise guaranteed not to reject: rejection is a defect. This distinction applies to `fetch`, D1 methods, R2 methods, DO stubs/storage, and `crypto.subtle` calls. ([`tryPromise` and `promise` declarations](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [Effect creating effects](https://effect.website/docs/v4/getting-started/creating-effects))
- Keep `run*` calls at the Worker/DO integration edge. `Effect.runPromise` resolves success and rejects on failure; v4's `Cause.squash` is the lossy conversion used by Promise/synchronous runners: it selects the first typed `Fail`, otherwise the first `Die`, otherwise a generic interruption/empty error. Thus a handler that must preserve typed failures, defects, and interruption separately should use `Effect.runPromiseExit`, inspect `Exit.isSuccess`/`Exit.isFailure`, and inspect the failure's `cause`; do not assume a rejection is a native `Error` or that it preserves a full Cause. `Cause.findError`/`findDefect` are the explicit unwrapping helpers, while `Cause.reasons` retains every `Fail`/`Die`/`Interrupt`. ([`runPromise`/`runPromiseExit`](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [`Cause.squash` and extraction APIs](https://unpkg.com/effect@4.0.1/dist/Cause.d.ts), [official running-effects guide](https://effect.website/docs/v4/getting-started/running-effects))
- `Effect.fail` represents a recoverable/expected error. Defects include uncaught exceptions and `Effect.die`; `Effect.catch` handles typed/recoverable failures only, not defects. Use `Effect.catchCause` only at a deliberate boundary where recovering from a full Cause (including defects) is correct; otherwise let defects remain visible. `runPromiseExit` is the safer error-observation boundary for converting an Effect result into the existing `{ error: { code, message, details? } }` HTTP envelope. ([`fail`/`die`/`catch` declarations](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [`Cause` model](https://unpkg.com/effect@4.0.1/dist/Cause.d.ts))

## Cancellation and cleanup

- `RunOptions.signal` interrupts the Effect fiber; the signal supplied by `tryPromise` is aborted on interruption. Abort is cooperative: the wrapped operation must observe the signal. Cloudflare's incoming `Request.signal` can represent client cancellation only when the documented request-signal compatibility flag is enabled; otherwise do not invent a cancellation guarantee. Pass the request signal to `runPromise`/`runPromiseExit` only when the handler's intended policy is to stop work on client disconnect. ([Effect `RunOptions` and Promise declarations](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts), [Cloudflare Request `signal`](https://developers.cloudflare.com/workers/runtime-apis/request/))
- `Effect.ensuring` runs its finalizer if the wrapped effect starts, on success, failure, or interruption. For acquired resources prefer `Effect.acquireUseRelease` or `Effect.acquireRelease` inside `Effect.scoped`: a scope closes on success, failure, or interruption; release receives the closing `Exit`; acquisition is uninterruptible by default. Finalizers are not permission, transaction, or durability guarantees for an already-returned Worker response. ([Effect resource-management guide](https://effect.website/docs/v4/resource-management/introduction), [`scoped`/`acquireRelease`/`ensuring` declarations](https://unpkg.com/effect@4.0.1/dist/Effect.d.ts))
- In Cloudflare, work that is neither awaited nor passed to `ctx.waitUntil()` may be canceled when the request ends. HTTP `waitUntil()` work gets at most 30 seconds after the response/client disconnect, shared across calls; canceled work must not be assumed to finish a D1/R2/DO write. Durable Objects remain active while handling requests or pending I/O; `DurableObjectState.waitUntil()` is not needed for normal request/RPC handling. Therefore use `await` for operations that determine the returned response, and use `ctx.waitUntil(Effect.runPromise(...))` only for explicitly best-effort post-response work with a bounded lifetime. ([Cloudflare Context `waitUntil`](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [DO state](https://developers.cloudflare.com/durable-objects/api/state/))

## Preserve the existing Cloudflare platform seams

- Request/Response remain standard Fetch objects. Cloudflare passes a `Request` to the module `fetch` handler and expects a `Response`; incoming Request properties are read-only, and request/response bodies are streams. Construct a new `Request`/`Response` when changing metadata. Do not make Effect's HTTP abstractions replace the public Worker handler or rewrite published user HTML. ([Cloudflare Fetch Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/), [Request API](https://developers.cloudflare.com/workers/runtime-apis/request/), [Response API](https://developers.cloudflare.com/workers/runtime-apis/response/))
- D1 remains the binding API: prepare/bind/run/raw/first/batch/exec return Promises and support generated Worker types and row generics. Preserve existing SQL, schema, transactions, and DTO shapes; `tryPromise` is only the typed adapter around each operation. D1 converts JS values to SQLite types on write, and `undefined` parameters are unsupported. ([Cloudflare D1 Worker Binding API](https://developers.cloudflare.com/d1/worker-api/), [Cloudflare D1 overview](https://developers.cloudflare.com/d1/))
- R2 remains the binding API. `get` may return `null`, and a successful body is a `ReadableStream`; `put`, `delete`, and `list` are asynchronous. Reads that are not consumed should have their body canceled to avoid memory/connection pressure; preserve current streaming/byte framing and encryption format rather than buffering or rewriting content as an Effect migration side effect. ([Cloudflare R2 Workers API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [Workers limits: simultaneous connections](https://developers.cloudflare.com/workers/platform/limits/))
- WebCrypto remains `globalThis.crypto.subtle` in Workers. Cloudflare documents the full Web Crypto surface with runtime-specific supported-algorithm differences from browsers and warns that Node Crypto is a separate API requiring `nodejs_compat`. Keep AES-GCM/PBKDF2/TOTP and byte framing on WebCrypto; adapt each Promise-returning primitive with `tryPromise` and preserve existing algorithm parameters. ([Cloudflare Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/))
- The existing Durable Object uses a namespace stub and `stub.fetch(...)` request/response boundary. DO calls can fail as remote exceptions; after a stub exception, Cloudflare says all in-flight and future calls on that stub fail and the caller must recreate the stub. Same-object calls have E-order delivery; different stubs have no ordering guarantee. Keep one Effect per remote call and do not hide/retry these failures in an adapter. ([Cloudflare DO Stub](https://developers.cloudflare.com/durable-objects/api/stub/), [DO API index](https://developers.cloudflare.com/durable-objects/api/))
- The configured DO is SQLite-backed but currently uses its asynchronous KV-shaped storage methods. Cloudflare documents that SQLite-backed DOs support both SQL and asynchronous KV APIs, with each storage method transactionally atomic/isolated; synchronous SQL cursors must be fully consumed before an `await` if SQL is ever used. Keep the current storage API and schema; do not silently migrate the limiter to SQL. ([Cloudflare SQLite-backed DO storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/))

## Runtime ceilings that constrain Effect composition

Cloudflare documents 128 MB per isolate, six simultaneous outbound connections waiting for response headers, 10,000 paid-plan subrequests per invocation by default, 64 MiB uncompressed Worker size, and no hard HTTP response-body size limit. CPU time is separate from network wait; the paid default is 30 seconds (configurable up to 5 minutes). Avoid unbounded `Effect.all(..., { concurrency: true })`, eager buffering of R2/HTML bodies, and detached fibers per request: these can hit connection, memory, subrequest, or lifecycle limits while still type-checking. ([Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/))

## Browser/workerd compatibility boundary

The Effect core package is an ES module with no declared runtime dependencies and its core Promise/AbortSignal/resource APIs use standard JavaScript/Web APIs. Cloudflare's Worker runtime supplies Fetch, Streams, AbortSignal, WebCrypto, and bindings, but its Worker-specific `Request`/`Response` types include extensions beyond `lib.dom` types. Generate `worker-configuration.d.ts` with `wrangler types` for the exact compatibility date, flags, and bindings, and keep platform-specific Worker types at the integration edge. Effect's `@effect/platform-browser` `BrowserRuntime` is browser-page lifecycle support (`pagehide` interruption), not a Cloudflare Worker adapter; do not import it to run the server Worker. ([npm package metadata](https://registry.npmjs.org/effect/4.0.1), [Cloudflare TypeScript guidance](https://developers.cloudflare.com/workers/languages/typescript/), [Effect BrowserRuntime](https://effect.website/docs/v4/api/platform-browser/BrowserRuntime), [Cloudflare Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/))

**Confidence: high.** Effect claims above are from the published `effect@4.0.1` declarations and official v4 guides; Cloudflare claims are from first-party runtime/API documentation. No runtime deployment or test was performed, so implementation-level compatibility beyond these documented contracts remains unverified.
